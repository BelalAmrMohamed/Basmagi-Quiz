### Same-name race condition (explicitly deferred by the prior audit)
`hasQuizNameCollision` (`api/_itemActions.js`) is a pre-check query, not an atomic DB constraint — unlike folders/courses, which are protected by real unique constraints (`folders_unique_name_per_parent`, `courses_unique_slot`) that a concurrent write can't slip past. Two concurrent renames/moves/edits landing on the same quiz title at the same course/folder can both pass the check and both succeed, producing a duplicate. The prior audit's fix-plan section explains why this was left out of scope ("a real fix would need a partial unique index... a schema change"). Design and implement that: a Postgres partial unique index on `quizzes` scoped to `(course_id, folder_id, lower(trim(title)))` (mind that `folder_id` is nullable — a plain unique index treats each `NULL` as distinct, so check whether you need two partial indexes or a `COALESCE`), a new Supabase migration file following the naming/style of the existing ones in `supabase/migrations/`, and update `handleRenameItem`/`handleUpdateQuiz`/`handleMoveItem` in `api/admin.js` to catch the resulting `23505` and return the same friendly error the pre-check already returns (matching how folder/course renames already handle their own `23505`) — keeping the app-level pre-check too isn't wrong (it gives a nicer error without needing to parse the DB error first), but the constraint is what actually closes the race.
